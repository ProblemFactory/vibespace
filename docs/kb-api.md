## API Reference

### REST Endpoints

#### Published pages (2.364.0)
- `GET /p/:id` — serve a published page. Middleware-exempt; module gates: private ⇒ cookie, public ⇒ open. Response always carries `Content-Security-Policy: sandbox allow-scripts …` (opaque origin — the XSS guard).
- `GET /api/pages` — list; `GET /api/pages/by-path?path=` — record for a source file (the explorer dialog's state probe).
- `POST /api/pages/publish` `{path, name?, public?}` — copy-in publish, upserts by source path (stable /p/<id>).
- `POST /api/pages/:id` `{public?, name?}` — flags; `DELETE /api/pages/:id` — unpublish.

- `GET /api/home` — home directory (+ authEnabled flag)
- `POST /api/login` / `POST /api/logout` — password auth (rate-limited; sets/revokes HttpOnly cookie token); `GET /login` login page
- `GET /api/backend-status` — CLI readiness for onboarding: {claude,codex} × {installed, version, loggedIn} (file-existence detection, never spawns CLIs)
- `GET /api/files?path=` — list directory
- `GET /api/file/info?path=` — file metadata (size, isBinary) without reading content
- `GET /api/file/content?path=` — read text file (max 10MB)
- `GET /api/file/raw?path=` — serve raw file (PDF, images)
- `GET /api/file/binary?path=&offset=&length=` — read binary chunk (max 1MB)
- `GET /api/file/excel?path=` — parse Excel → JSON
- `GET /api/file/docx?path=` — parse Word → HTML
- `GET /api/file/csv?path=&offset=&limit=&sep=` — streaming CSV/TSV row range (virtual scroll)
- `POST /api/format` — server-side code formatting (Python/Go/Rust/Shell via ruff/black/shfmt/gofmt/rustfmt)
- `GET /api/download?path=` — download file
- `POST /api/upload` — multipart upload (fileNames JSON field for Unicode filenames, preservePaths=1 for folder uploads with recursive mkdir)
- `GET /api/file/serve/*` — path-based raw file serving (enables `<base href>` for HTML preview relative paths)
- `POST /api/file/write` — write file
- `POST /api/mkdir` — create directory
- `POST /api/rename` — rename
- `DELETE /api/file?path=` — delete
- `POST /api/archive` — create archive from same-parent paths[] (`.zip`/`.tar[.gz|.bz2|.xz]`, execFile zip/tar, 409 on existing dest unless overwrite)
- `GET /api/archive/list?path=` — archive contents (unzip -l / tar -tvf parse; 20k entry cap)
- `POST /api/archive/extract` — extract archive to dest (never overwrites unless overwrite:true — unzip -n / tar -k)
- `POST /api/archive/extract-entry` — extract ONE entry to a temp file (spawn streaming, 200MB cap) → client opens via normal viewer pipeline
- `POST /api/file/copy` / `POST /api/file/move` — recursive copy/move to FULL dest path (fs.cpSync; move falls back to copy+rm across devices; 409 on conflict unless overwrite). `progress:1` (2.215.0) → returns `{opId}` immediately and runs as a polled op: `GET /api/file/transfer-status?id=` {done,total(bytes),status,error,dest}, `DELETE` cancels (best-effort; local worker copies can't abort mid-flight). Cross-host relays count bytes INLINE on the tar/cat stream (du -sb pre-computes total, BSD -sk×1024 fallback); local/same-host branches poll du on dest. In op mode the 409-exists check surfaces as op error 'exists' — the client maps it back onto the confirm-overwrite flow. Paste always requests progress; the client row renders only if the op outlives 400ms (small pastes look unchanged)
- `GET /api/download-zip?path=` — stream folder as zip download (spawn `zip -r - `, no temp file)
- `GET /api/file/stat?path=&du=1` — extended properties (mode/uid/entryCount; optional bounded du -sb)
- `GET /api/dir-complete?path=` — directory autocomplete (500ms timeout, supports `~`)
- `GET /api/fonts` — system monospace fonts via `fc-list` (cached, fallback for client-side detection)
- `POST /api/custom-grids` — add custom grid preset `{rows, cols}`
- `DELETE /api/custom-grids` — remove custom grid preset `{rows, cols}`

**Input queue (`queue-op`, 2026-09-06)**: `{type:'queue-op', sessionId, op:'steer'|'remove'|'steer-all', id}` — act on a message the user sent DURING a running turn. Validated against the harness's `backend-caps` `inputModes {queue, steer, queueOps}` row (NEVER a backend id), then formatted by the adapter's `formatQueueOp` and written to the wrapper's stdin. A SECOND gate follows it: the RUNNING wrapper's own `caps.inputQueue` advert (`wrapperCaps()` over the sidecar the wrapper writes) **or** the in-band proof that it has already published a `queue_changed` (a REMOTE wrapper's sidecar lives on ITS machine) — a session spawned before this release passes the caps row and would have its frame dropped silently (2.361.1/2.364.1), so it is refused with "its agent predates the input-queue update … Terminate + Resume". Every refusal answers `{type:'error', code:'queue-op-unsupported', scope:'action', sessionId, error, message}` naming the harness and what it CAN do. **A per-session `error` is a SCOPED refusal (renders in-chat, window untouched) only when it carries `scope:'action'` or one of the client's explicit codes (`input-rejected`, `not-codex-chat`, `queue-op-unsupported`)** — "any code is scoped" is wrong: `ended-during-attach` is coded AND fatal, and must keep taking the view-only rescue + Resume bar. Wrapper → server events (inside the normal record stream): `queued_input {msg_id, turn_id}`, `queue_changed {items:[{id, msgId, preview, ts, kind, from}], turn_id}` (the WHOLE queue on every change — the app-server's own `thread/queue/changed` carries no items, so the wrapper re-`list`s), `queue_op_result {op, id, msg_id, ok, reason, detail}`. The normalizer turns `queue_changed` into `{op:'meta', subtype:'queue', items}` (session state — never a transcript message) and stamps the originating user bubble with `queueState: 'queued'|'steered'|'removed'|null` through the ordinary `edit` op. `attached` and `created` both carry `queue` (the normalizer's `queueState()`) **and `queueSupported`** (attach: the wrapper's sidecar advert OR the normalizer having seen a `queue_changed`; create: always `false` — a just-spawned wrapper has reported nothing yet, and its baseline `queue_changed` turns the controls on moments later), so a reconnecting or newly created window starts from a fact. A `queued_input` from a wrapper that never published a queue falls back to the old system card instead of stamping a chip that could never clear.

**`permission-response` → the CLI (lane L, 2026-09-25)**: `permissionUpdates` (the card's "Always Allow") reaches claude's stdin as `updatedPermissions` inside the allow response (`ClaudeCodeAdapter.buildPermissionResponse`) — the 2.1.281 stdio result schema's own key; the old `permission_updates` was stripped on arrival, so no rule was ever applied. For VibeSpace's own tools the client sends the WIDENED suggestion (`widenSuggestions`, src/agent-tool-rules.js); r2: for a HELD verb or tool the NARROWED one (the exact command line, never `<tool> <verb> *`), and nothing at all for an ask verb (`vibespace-page publish` — the card offers no Always Allow). The spawn flag itself did not change: claude spawns already carried one inline `--settings` JSON, which now also holds `permissions.allow` for those tools (row `claude.allowAgentTools`, default ON).

**OpenCode ask cards (S9 remainder, B-eac2)**: `permission-response` gained `via` (+ `host`). A card built from an OpenCode `question` tool declares `via:'opencode-serve'`, and the ws layer answers it on the SERVE's own route instead of a session's stdin — the conversation may have no live process here at all (a stopped conversation opened read-only can still show a pending ask). The card itself stays harness-neutral: it forwards what the record that created it declared, never a backend id. A refusal answers `{type:'error', scope:'action', code:'opencode-question', requestId, error}` — the card flips itself to "answered" optimistically, so silence would be a lie, and `scope:'action'` is load-bearing: without it a session-scoped `error` frame is read as "attach failed" and flips the LIVE window into the read-only Resume bar (the 2.363.1 law — a refusal rejects ONE action, it never condemns the conversation). Server → client `opencode-updated` `{kind:'revert'|'unrevert'|'question-replied'|'question-rejected'|'store', sessionId, requestId?, revert?, host?, reason?}` is the multi-client echo: every browser re-polls the session list and any open window on that conversation says in-line what happened. `kind:'store'` is the LIVE LANE's own invalidation (cache invalidation must NOTIFY): the SSE stream or the sqlite watch saw a change nobody asked about — including one made by a TUI on the same store — and the push is what makes it appear without waiting for that browser's 5s poll. It is COALESCED server-side (`OPENCODE_CHANGE_COALESCE_MS`, 2s) and streamed message parts are deliberately excluded, because each push costs every client one discovery sweep.

**OpenCode serve terminal (S9 remainder piece (c))**: `create` gained `opencodePty:true` — the session's pty is one the OpenCode SERVE owns (`POST /pty` on the serve, streamed over `GET /pty/{id}/connect`) instead of a local dtach spawn. src/server/opencode-pty-bridge.js connects that websocket SERVER-SIDE and hands the session layer the same `{pid,onData,onExit,write,resize,kill}` shim the daemon pipe-session uses, so xterm, input, resize and the buffer file work unchanged. The serve's port, its Basic auth header and its connect ticket NEVER reach the browser.

**`attached.messages` = the TEXT WINDOW (2.369.167, perf lane A)**: the live attach AND the view-only attach ship `normalizer.tailWindow()` — the tail counted in text cards (src/text-window.js; 50–400 records, ≤ 128 KiB past the 50-record floor since perf r1), not tail(50). `totalCount` unchanged. A pure deterministic function of the message list, so a same-epoch re-attach ships the same slab and the client's identical-skip (2.369.2) fires. No protocol field, no capability: an old client renders any N. Sub-agent attaches (`sub-*`) still send their full list.

**`attach {slab: 'floor'|'text'}` (2.369.167, perf r1)**: the web client says which slab it wants — `'floor'` = exactly tail(50) (the pre-lane slab) for a SUSPENDED view (a hidden window's queued re-attach) or a displayed one while any other attach is in flight on the socket (a cold open of N windows, a page reload, a reconnect's displayed windows: only the FIRST of the burst gets the text window); `'text'` (or absent — an older client) = the text window. Both the live and the view-only attach honour it (`tailWindow(attachWindowOpts(data.slab))`, src/text-window.js — the ONE mapping); a held resume (`slab:'held'` on the REPLY) ignores it (no slab). An old server ignores the field (it ships its own window). Additive: no capability gate needed in either direction.

**Resume by seq — `attach {sinceSeq, sinceEpoch, caps}`, `attached {opSeq, replay, slab}`, `lagged`, `msg.seq` (2.369.167, perf lane chunk D — the one wire change)**: every `msg` frame of a session's OWN normalizer (sessionId = the session; a subagent virtual session's frames are not stamped) carries `seq`, a per-session number from the session's op ring (src/op-seq.js; ≤ 2000 frames / ≤ 4 MiB, the exact text sent; reset — never renumbered — when rebuildHistory mints a new `normEpoch`). Client → server: every `attach` the web client sends carries `caps:['op-seq']` (src/lib/ws.js adds it at the wire), and a live ChatView's re-attach adds `sinceSeq` (the last seq it APPLIED) + `sinceEpoch` (the epoch that seq belongs to) — ONLY after it has seen `opSeq` from this server. Server → client: `attached` always carries `opSeq` (the last seq this socket is current to — the capability advert). When `sinceEpoch === normEpoch` and the ring still holds every frame after `sinceSeq`, the reply is `attached {…every live fact of the full payload, opSeq, slab:'held', replay:[the frames after sinceSeq, verbatim]}` with NO `messages` and NO `turnMap`; the client applies the live facts and runs the replay through `_onOp` (nothing rebuilt, compared or fetched). Otherwise (no since, another epoch, a seq outside the ring or never handed out) the full `attached` as before + `opSeq`. The `attach-ack` still precedes both; the reply is written synchronously after the verdict, so a replay is followed by exactly the later live frames. `lagged {sessionId, normEpoch, seq}`: sent ONCE to a client that advertised `op-seq`, has been answered by an `attached`, and whose socket's `bufferedAmount` exceeds 4 MiB when a stamped frame is due; that session's `msg` frames are then skipped for that socket until it re-attaches (seq = the last frame it was handed); telemetry event `ws-lagged` (the queue size). The client answers with `_reattach` (resume by seq). A client that did not advertise the capability is never cut (today's unbounded delivery — it cannot answer). Old client: sends no since, ignores `seq`/`opSeq`/`lagged`. Old server: never sends `opSeq`, so the client never asks. **perf r1: `sinceSeq` is the last seq the view APPLIED with every earlier op applied too — `_onOp` advances it only after the op ran, and an op that throws POISONS it: the view's next attach carries no `sinceSeq` (the server's full rung) and a same-epoch full reply is rebuilt from its slab (`_fullViewReset`), never caught up from `_windowEnd`. No wire change beyond the omission.**

**Virtual session attach**: `attach` with `sessionId` starting with `sub-` routes to subagent handler. `sub-{parentToolUseId}` returns live-buffered messages from parent session's `subagentBuffers`. `sub-agent-{agentId}` loads completed agent's JSONL from disk. Both respond with standard `attached` payload with normalized messages. Live virtual sessions receive normalized `msg` ops via per-subagent normalizers. `attach` with `viewOnly:true` loads JSONL history without an active session (for stopped session history viewing).


## Channels — the communication panel (P0a, docs/design-communication-panel.zh.md)

EVERY route takes `host` and passes it down: `hostId` is a PARAMETER, never a
branch (decision 15). v1 serves THIS machine only, and that is a NAMED refusal
(`501 host-not-served`) for anything else — a silent local answer to a
question about another machine is the failure the rule exists to stop.

- `GET /api/channels[?host=]` — the index DIGEST: adapters (with their
  resolved lane), conversations (title/kind/participants/lastAt/unread/tracked),
  each conversation's resolved `convCaps`, its `offers` (read / send-as-user /
  send-as-bot, each `{offered, why}`), its `identityWarning`
  `{level, marking, verbatim}` and its `freshness` claim
  `{kind, state, seconds, why?}` — `state:'off'` with `why`
  (`untracked` / `adapter-disabled` / the scan resolver's own reason) for a row
  nothing will ever fetch (r3), rendered "not polling" / "not scanning" — plus
  `unreadTotal`. Each conversation's `lane` is `{via, why, source}` as the
  resolver answered it, and on a scan lane `source` is exactly what the ingest
  was gated on (r3): `source:null` means nothing was ingested. **Never message bodies, and
  never a composed human SENTENCE**: this payload is broadcast to every client
  at once while the language is per DEVICE, so the client renders the words
  from the structure (`channelCaps.freshnessText` / `identityWarningText`).
  Each adapter's `auth` is `{state: connected|expired|unknown, why, expiresAt}`
  — a RESOLUTION, never a stub. **r3 (agent groups):** each adapter row carries
  `sendStartsTurn` (a send there wakes an agent = a billed turn — the module's
  declaration), and the digest carries `quarantined:[{file, to, why, at,
  blocked}]` — every store file set aside (or BLOCKED: `to:null`) at boot,
  on the first screen.
- `GET /api/channels/:adapterId/:convId[?host=]` — one conversation's summary
  plus its adapter row (what the window's context bar shows). 404 with a reason.
- `GET /api/channels/:adapterId/:convId/messages?before=&beforeId=&limit=` —
  ONE page of normalized `ChannelRecord`s, oldest-first by `(at, vendorId)`,
  strictly before the BOUNDARY RECORD `(before, beforeId)`. `limit` is clamped
  to 200. **The boundary is a PAIR, not an instant**: `at` is not unique (a
  Lark burst shares a millisecond, Gmail's `internalDate` is second-derived)
  and paging on it alone stranded every record of such a group at or after a
  page boundary. `beforeId` is that record's `vendorId`, which invariant 2
  makes unique per conversation; omitting it is still terminating but lossy.
  **The reader seeks as far back as the writer keeps (r3)**: it used to read
  only the newest 2 MiB, so a page boundary past that answered `[]` for ever
  while retention kept the records; it now walks earlier windows until the
  page is full or byte 0 is reached.
- `POST /api/channels/:adapterId/:convId/read` `{at?}` — mark read; the engine
  re-derives `unread` from the log rather than trusting a counter, and with no
  `at` the instant is the NEWEST RECORD's — for future-dated records (with
  `now()` a future-dated vendor record keeps `unread` above zero for ever) AND
  for past-stamped ones (r3: the r2 spelling was `max(now(), newest.at)`, so
  for every real adapter a message stamped before the mark but fetched after
  it was silently marked read). With no record at all the mark is left where
  it was. **404 on an id this instance does not hold** — a route may not mint
  an index row — and a mark that changed nothing broadcasts nothing.
- `POST /api/channels/:adapterId/:convId/track` `{tracked}` — the opt-in that
  decides whether anything is ingested at all. Tracking refreshes that
  conversation's `convCaps` (one of its three named refresh triggers),
  BROADCASTS the persisted change (r3 — it used to rely on the pass it kicks,
  which a spent request budget returns from before notifying), and then kicks
  a pass. 404 on an id nobody has discovered.

  §13; every failure answers `{error, code, detail}` with a status BY CODE:
  `409 needs-credentials` = the row's integration resolves to none — the
  client opens the Integrations card FIRST; `501 not-supported` = an
  undeclared capability / a kind with no consent flow; `401 auth-expired`;
  `502` = a vendor refusal; `404 no-such-adapter`).
  - **r4 (2.369.165, docs/design-integrations-per-account.zh.md §2.4) — the
    account dialog's sign-in, the storage consent block's shapes, for an
    account that does NOT exist yet.** A CLIENT CHOICE in any body below is
    `credentialKey` (`cluster:<presetKey>` | `custom`), `clientPreset:'<k>'`
    (the storage dialog's spelling), `credential {appId, appSecret}` or
    `clientId` + `clientSecret` (a custom client — sealed under
    `.channels-key` at once, echoed nowhere); refusals `400 unknown-credential`
    / `invalid-client` (`detail.errors` = field → rule, never a value) /
    `own-retired`.

## Per-session git worktree + claude's agent→user channel (owner rulings 9 and 8(c))

**`create` gains `worktree: true`** (claude only, gated on the `backend-caps` `worktree` row — never a backend id). The server PREFLIGHTS it before spawning, because `--worktree` makes the CLI exit 1 outside a git repo BEFORE the session exists and the window would die instantly with the reason buried in the buffer. Two refusals, both `scope:'action'` (they render in chat and leave live windows alone):
- `{type:'error', code:'worktree-unsupported', scope:'action', reqId}` — the harness has no such flag.
- `{type:'error', code:'worktree-not-a-git-repo', scope:'action', reqId, cwd, hostName?}` — the message names the cwd, the machine, and the CLI's own escape hatch (`git init`, or a `WorktreeCreate` hook in settings.json for another VCS).

The probe runs against a machine HANDLE (`hostId` is a parameter): locally a bounded `git -C <cwd> rev-parse --is-inside-work-tree`, remotely ONE `hosts._hostShell` round trip that answers both halves of the CLI's own `hook OR repo` gate. A probe that cannot ANSWER (timeout, unreachable) is not a refusal — the spawn proceeds and the CLI speaks for itself. The flag itself is emitted by the ADAPTER (`worktreeSpawnArgs`): new ⇒ yes, fork ⇒ yes, **plain resume ⇒ never** (the CLI re-enters its own recorded worktree; a second flag = a second tree). Remote spawns carry it with no transport special-casing at all — it is just another `spec.args` entry that `buildRemoteExec` quotes (`scripts/test-remote-shell.mjs` drift guard). **`--tmux` is never emitted on any path.**

**`active-sessions`, `attached` and `created` all carry `worktree` (boolean) and `worktreePath` (string|null)** — `worktree` is what THIS RUN is, `worktreePath` is the directory the CLI itself announced in its `system/init` frame. `created` carries them for the 2.368.4 reason: the creator window never receives an `attached`, and it is the window that has to draw the badge. **On the client they reach every surface through `LIVE_SESSION_FACTS` in src/lib/sidebar.js** — `_merge()` rebuilds the session row rather than spreading it, so a live fact that is not on that list never reaches the card, Session Properties or the fork; a new payload key must be added there (or to the renamed/derived set) or the drift guard in scripts/test-worktree-userchan-ui.mjs fails.

**`worktree-path` (server → client)**: `{type:'worktree-path', sessionId, worktree: boolean, worktreePath: string|null}` — the init-frame ARBITER, pushed on a CHANGE only (an unchanged re-attach frame is a no-op, so a reconnect storm cannot flap the badge). `worktree:false` is the CLI saying this run is NOT isolated (its worktree was gone — "The worktree binding has been cleared." — or a resume could not create one); the client drops the live badge and **does not** write that back over the user's saved pick.

**"Same cwd" is the QUESTION, not the verdict (2026-09-07 round 4).** The arbiter used to retire the fact whenever the announced cwd equalled the launch cwd — a NEGATIVE inference, and a plain RESUME of a worktree conversation satisfies it: a resume launches in the DISCOVERY cwd, and for such a conversation that IS the worktree (the CLI wrote its transcript from in there, so the JSONL's own `cwd` and the project-dir encoding both name it — measured: `claude --worktree` in `/tmp/vs-wtrepo-probe` produced `~/.claude/projects/-tmp-vs-wtrepo-probe--claude-worktrees-probe9`). So every resumed worktree session was reported as not isolated, permanently, because boot-restore reads `_worktree: !!meta.worktree`. The positive question — *is the announced directory a LINKED worktree?* — is answered by git itself (`rev-parse --git-dir --git-common-dir` differ inside one, agree in a plain checkout), asked at most ONCE per attach per directory, bounded and async, against the machine the session runs on (`hostId` is a PARAMETER: a local child process, or ONE `hosts._hostShell` round trip answering in `__VS_WT_YES__`/`__VS_WT_NO__` markers — never an exit code, because "not a repo" and "git is missing" are different answers). **A probe that cannot ANSWER touches NOTHING** (the ws-create preflight's tri-state rule) and says so in the log + a `worktree-probe-unknown` event. Known limit: a `WorktreeCreate` hook can isolate a run under another VCS, and such a directory also answers "not a git repo" — a resume that re-enters it in place retires the badge.

**`user-file-published` (server → client)**: `{type:'user-file-published', sessionId, toolCallId, files:[{path, name, link?, pageId?, size?, error?}]}` — the result of ONE `SendUserFile` tool call. `link` is a **RELATIVE** `/p/<id>` (the 2.366.1 URL law: the server never guesses an absolute URL; the browser joins it with its own origin). Pages are session-owned and **private by default**. Every failure (missing file, too large, unreadable, publishing unavailable) rides the same message as a per-file `error` and lands ON the card — a file the agent believes it delivered and the user never received is not allowed to be silent.
