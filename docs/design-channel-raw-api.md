# VibeSpace — Channels RAW API pass-through (design, 2026-10-02 04:30 PDT; the owner's direction after rejecting the sync-mount idea: "只需要提供快捷的鉴权透传能力", Google Drive-class vendors keep Remote mounts)

## 0. The one idea
VibeSpace maintains NO vendor API mapping. An agent sends a raw HTTP call (method + path + query/body) through VibeSpace; VibeSpace adds the account's auth, holds the fence (which credential, which tier, which hosts, how much), records every call, and turns a write into a proposal the user approves. The agent learns the vendor's API from the vendor's own docs — the CLI tells it where they are.

## 1. The CLI (the agent side; vsst_ token; every verb = one audit line)
```
vibespace-channels api creds                         # the credentials this conversation may use: id · vendor · tier (read | write-ask | write-auto) · calls left this minute/day
vibespace-channels api docs <cred>                   # the vendor's API reference URLs (Lark open platform / Google API refs), the API base host(s), the token's GRANTED scopes, two examples — nothing else is "known" by VibeSpace
vibespace-channels api <cred> GET  /open-apis/docx/v1/documents/<id>/raw_content [--query k=v]… [--max-bytes N] [--out <file>]
vibespace-channels api <cred> POST /open-apis/... --json '{…}' | --body-file f.json | --upload f --field k=v    # a write ⇒ a proposal unless the grant is write-auto
vibespace-channels api wait <id> [--timeout 120]     # the proposal's outcome (free; else it rides the next turn like a channel receipt)
vibespace-channels api log [--last 20]               # this conversation's own calls (audit view)
vibespace-channels api request <cred> --tier read|write --why "…"   # the existing request door (For-you item; the user grants)
```
Result = `{status, headers (allow-listed), body}` JSON pretty-printed, ≤ 1 MiB unless `--out` (saved only under the project / tmp / ~/Downloads — the browser CLI's write_path_refused rule); binary only with `--out`. Refusals by name: `api_not_granted` (→ request), `api_tier_read` (a write under a read grant), `api_pending <id>` (a proposal filed), `api_host_refused`, `api_budget` (per-minute / per-day, the vendor's 429 as the account's rate ladder — lark-threads' judge), `api_sensitive_ask` (always a proposal), `api_cred_expired` (re-authorize, the user's).

## 2. The fence (PURE src/channel-api.js; every rule a table row with a control)
- CREDENTIAL = a Channels account (Lark, Gmail…) or a Google storage mount's OAuth (Drive/Gmail/Calendar…); the token NEVER leaves the server (the CLI calls /api/agent/channels/api; VibeSpace sets Authorization; Authorization/Cookie/Host from the agent are dropped; other headers pass).
- HOST = the vendor's own API hosts only (the adapter's EGRESS list: open.feishu.cn / open.larksuite.com; googleapis.com family) — the agent gives a PATH, never a URL; redirects to another host are not followed; 30 s timeout; the response bounded.
- TIER per (credential, principal) on the EXISTING access row (channel-acl's levels + origins, widen-only, requestable in the middle): `api: none (default) | read | write-ask | write-auto`. `read` = GET/HEAD + the vendor's read-by-POST patterns (a TINY vendor table: Lark `/search`, `/batch_get`, `/query`, `/list`; Google `:batchGet`) — anything else is a write. `write-ask` = every write is a proposal. `write-auto` = writes run, EXCEPT the SENSITIVE class.
- SENSITIVE (always a proposal, never auto, never "always allow"): DELETE; paths matching the vendor's tiny list (Lark: `/permission`, `/member`, `/transfer`, `/delete`, `/remove`, `/admin`, `/approval`, `/pay`; Google: `/permissions`, `trash`, `delete`, `/acl`); a body > 256 KiB; an upload.
- BUDGET: the account's vendor meter (shared with the channel's own reads, 60/min Lark) + a per-grant cap (default 30/min, 1 000/day per conversation, settable on the grant); a 429 enters the account's rate ladder (never a retry loop).
- PEER CONTENT: string values in a response are peer text toward an agent — the peer-text belt (toAgentText) over every string ≤ the frame rule (a census row); tokens in a response body (`refresh_token`, `access_token`, `Authorization`) are redacted by the secret-shape redaction at the writer (exit-run's rule) before the agent or the audit sees them.

## 3. The UI (the user side; words zh/ja)
- Channels panel → account card → **API access…** dialog: the principal picker (the Grant access… precedent, multi-select), a tier per principal (Off / Read / Read + write, ask each / Read + write, auto — sensitive still asks), the daily cap, the vendor's sensitive list (read-only, with "DELETE and these paths always ask"), the "Always allowed" patterns this user approved from cards (method + path pattern, per conversation, revocable here). Default: Off for everyone; a new account's card says "Agents cannot call this API until you grant it".
- The proposal card (the outbox card shape, in the chat AND in the Outbox): "<agent> wants to call Lark · POST /open-apis/docx/v1/documents — create a document" (the head = the vendor's method + path; the body collapsible, pretty JSON, ≤ 4 KiB shown, the rest "N KB more"), Approve ▾ (Run now / Run and always allow this call shape for this conversation — never for a sensitive one) / Reject (with a reason the agent reads); the result lands back on the agent's turn; "what you approve is what runs" — the frozen request bytes are what the Approve sends. A For-you item per pending proposal (origin channels), one per card.
- **API log** (the account card's tab + Activity): one row per call — time · conversation · method · path (query keys only) · status · duration · bytes · verdict (ok / refused <code> / approved by <user> at <time>) · the approval link; filter by conversation/status; the record-clear tool applies to bodies. Bodies of WRITES live in the proposal record (part of what the user approved); bodies of reads are not stored (size + sha256 only). Storage: data/channels/<account>/api-audit.ndjson, date-rolled, 16 MB ring (the exit-run precedent).
- The status bar's `channels` chip counts this turn's API calls ("3 API calls · 1 awaiting you"); the tool card in the chat gets the keyed call rows (the channel-touch precedent) so a human reading the transcript sees what the agent called.

## 4. What stays out (by the owner's rule: no mapping)
No per-vendor SDK, no path→meaning table beyond the two tiny lists (read-by-POST, sensitive), no response schemas, no pagination helpers — the agent reads the vendor's docs. Google Drive FILES stay a Remote mount (rclone); the raw API is for everything the mount does not express (Docs/Sheets/Calendar/Gmail labels…).

## 5. Cost + gates
One lane (build, Opus) + one authority-class verify (Fable): PURE channel-api tables (tier × method × path class ⇒ run / proposal / refused, with controls), the route + CLI over the real engine with a fake vendor (host fence, header stripping, body bound, 429 → ladder, the secret redaction, the belt census row), the proposal card + Approve runs the frozen bytes (test-channel-outbox shape), the API log + record-clear census, test-vendor-whitelist (the pass-through is ONE allow-listed vendor surface, gated by the grant), test-spend-paths (no billed turn is started by a call — the result rides the agent's own turn), i18n. ≈ 1.5 days.

## 6. Owner decisions (one yes/no each)
D1 Default tier for a newly granted principal = Read (writes need a second click)? — recommend yes.
D2 "Always allow this call shape" offered on non-sensitive write cards (per conversation, revocable)? — recommend yes.
D3 Google credentials: both the Channels Gmail account and a storage mount's Google OAuth are usable as `<cred>`? — recommend yes (one picker, labelled by source).

## 7. As built (2.369.212, lane channel-api-core, 2026-10-04)
- **PURE fence** `src/channel-api.js` — every §2 rule a table row; `scripts/test-channel-api.mjs` ① runs each row on the module and on a mutant copy with that rule taken out (19 rows, 19 controls). The tier is channel-acl's own axis (`API_TIERS`, `effectiveApi`, origin `api`, level `hidden`, widen-only MAX over agent / group / All rows), stored in its OWN index table `apiGrants` — so an API grant never widens reach and never appears as an access row (the access rows' writers rewrite whole rows; a separate table keeps the two axes from erasing each other).
- **Headers**: `Authorization` / `Cookie` / `Host` / `Proxy-Authorization` are REFUSED by name (not silently dropped — the agent learns the token is VibeSpace's); other headers pass only from a small allowlist.
- **Hosts** (since lane channel-api-declared each list is DECLARED by its owner — §8): Lark `open.feishu.cn` / `open.larksuite.com`; Slack `slack.com`; Google `www.googleapis.com` + gmail / docs / sheets / slides / drive / people / tasks `.googleapis.com` (`--host` picks one; default the first). Redirects: on-host followed (≤ 3), off-host refused (`api_redirect_refused`), the token never leaves the host.
- **Credentials (D3)**: a Channels account (Lark / Slack / Gmail — the adapter's own `apiBearer`) or `mount:<id>` (a Google storage mount's OAuth token via `mounts.oauthTokenOf`, refreshed in memory with the mount's own client through the same ONE fetch site).
- **Orchestrator** `src/server/channel-api.js` — the tier asked first and after every await (test-architecture §65c, with controls); ONE fetch site (`vendorFetch`, test-vendor-whitelist §14, with controls); the account meter (`apiCredential().gate()` = back-off / minute budget / agents' share, `charge()` as `agent`, a 429 → the account's back-off); the per-grant budget (30 / min, 1 000 / day per conversation, `perDay` settable on the grant); the belt (secret-shapes + toAgentText on every string, token-named keys redacted; test-peer-text-census door `apiAnswer`); the audit ring data/channels/<cred>/api.ndjson (16 MB, rolled once — size-rolled, not date-rolled).
- **Proposals**: frozen request (method, host, path, query, headers, base64 body, sha256 digest) in data/channels/api-proposals.json; Approve re-derives the digest and runs nothing on a mismatch; "Run and always allow this call shape" (D2) stores (credential, conversation, method + host + path with id-like segments as `*`) — never offered for a sensitive call; revocable in the dialog.
- **UI**: "API access…" on Lark / Slack / Gmail account cards (one credential picker labelled by source; principal picker, new picks at Read — D1; tier + calls-a-day per principal; the sensitive list; always-allowed shapes with Revoke; the waiting proposal cards; the API log). The chat's call rows ride the §26 witness (touch op `api`, one row per call; a row opens the dialog).
- **ONE proposal = ONE card** (lane channel-api-ui): PURE `src/channel-api-card.js` draws it in the chat (under the call row), the Outbox ("API calls": one row per proposal, its card under it), the dialog and ONE For-you item (origin `channels`, Approve / Reject naming the frozen digest; resolved WITH the outcome). The card: the frozen request (method, host, path, query, headers, body's first 400 chars + size + sha256), the tier, the sensitive reason, "Run and always allow <shape>" only for a non-sensitive write. `src/server/channel-api-cards.js` hands the agent its receipt on its next turn (ran: status + bytes / rejected by whom / expired / withdrawn — `api wait` is a convenience), expires a proposal unanswered for 24 h and withdraws one whose account was removed or tier withdrawn (by name, nothing runs).
- **Not built** (named, for the verify / a follow-up): the heavy chrome leg of the cards (lane channel-api-ui ran out of budget); `api request --tier` (the refusal names the user's door instead); multipart `--upload` (a raw `--body` with a multipart content type is accepted and always asks); the status-bar chip's "· 1 awaiting you" wording.

- **As built in a browser** (lane channel-api-chrome, scripts/test-channel-api-chrome.mjs): the registry now carries `apiBearer` (a real account could not run an approved call before); All agents stay at Read unless the dialog's own tick (`allWrite`) widens them; the sensitive list and the log are worded; the card / Outbox / dialog wrap at 390 px. Open: the on-host 307/308 redirect is not yet judged by the fence (verify LOW).

**Verify r1 (adversarial) rules.** A dot segment in any spelling (`.%2e`, `%2E.`, `%2e`) is refused — the class is judged on the path the fetch sends. A call SHAPE wildcards ids only (a segment with a digit and no "."); method names (`chat.postMessage`, `values_batch_update`) and a `:verb` suffix stay literal. A tier below "Read + write" ends that principal's always-allowed shapes. One conversation keeps at most 10 proposals waiting per credential, and each proposal counts in the budget. Approve carries the card's digest (a changed record runs nothing). A mount's token refresh is single-flight and paused 60 s after a refusal. The bearer is cut out of every answer (binary too). A revoke after the vendor answered audits `withheld` with the vendor's status. POST batch deletes (`batch_delete`, `batchDelete`) are sensitive.

## 8. The api row — the vendor facts live in the vendor's file (lane channel-api-declared, 2026-10-04)
The owner: "我需要当前系统低耦合" — "sensitive path 定义在每个 vendor 自己的文件里；保持通用内部接口格式；拓展 vendor 只需要 vendor-specific 的文件 + 一行注册". The central `VENDORS` / `KIND_VENDOR` tables of `src/channel-api.js` are gone (test-architecture §77 keeps them gone and keeps the fence + orchestrator free of any vendor name). Each adapter declares ONE row on its registry module (`adapter.api`, the `API_ROW` constant beside its `apiBearer`); the engine hands it on the credential (`apiCredential(id).api`) and lists as raw-API accounts exactly the kinds whose adapter declares one; the fence reads it through `vendorRowOf(cred)`; `vendorFetch` reaches only the hosts of the credential's own row.

**The schema** (ONE, validated by the registry — `src/channels/index.js` `validateApi`; a bad row THROWS at `register`, an `apiBearer` without a row or a row without an `apiBearer` THROWS at `create`, like an undeclared capability):

| key | type | meaning |
|---|---|---|
| `label` | string, 1–60 chars | the vendor's name as `api docs` and the API access dialog say it |
| `hosts` | non-empty list of bare lowercase hostnames (no scheme / port / path) | the API hosts; `hosts[0]` is the default, `--host` may name another, never one outside the list |
| `docs` | non-empty list of https URLs | the vendor's own API reference — VibeSpace keeps no API map of its own |
| `readByPost` | list of RegExp, or strings anchored with `^` | the vendor's paths where a POST reads (no proposal under "ask each") |
| `sensitive` | list of RegExp, or strings anchored with `^` | the paths that ALWAYS ask — never auto, never "always allow" (DELETE, a body over 256 KiB and an upload are sensitive for every vendor, in the core) |
| `refresh` | optional https URL | the token endpoint VibeSpace itself refreshes the credential at — only a storage mount's lent token (src/mounts.js `OAUTH_API`); a channel adapter refreshes inside its own `apiBearer` |

The storage-mount credential (D3) takes its row from `src/mounts.js` (`MountManager.OAUTH_API`, read through `oauthApiRows()`), not from `src/integration-registry.js`: the registry's Gmail row is the Gmail CHANNEL's account-dialog client (fields, a delegate to the drive presets) and declares no hosts, while MountManager owns the storage OAuth clients (`OAUTH_CLIENT_VENDOR`, `oauthClientOf`, `oauthTokenOf` — the D3 bearer's source), so the row and its token endpoint (`oauth2.googleapis.com`, gone from the orchestrator) sit with them. Its hosts / lists are the values the old `google` row held (behaviour identical).

### Adding an integration (the checklist)
1. **The adapter file** `src/channels/<kind>.js`: the instance's `apiBearer()` (the account's token, refreshed inside the adapter) + the module's `api` row (the schema above) on its registry object.
2. **Its egress**: every host of the row in the adapter's own `EGRESS` (test-channels-egress derives the census from the row — a row host missing from `EGRESS` is red; the `docs` URLs are documentation and are not egress).
3. **The one registration line**: the module in `REAL_ADAPTERS` (src/server/channels-engine.js) — the same line every adapter already takes.

Nothing else: not the fence, not the orchestrator, not the card, not the CLI (test-channel-api ⑥ proves it — a fake vendor `acme` = one scratch adapter file + one entry in a copy of the `REAL_ADAPTERS` line runs a read, a read-by-POST, a sensitive proposal + its card, `docs` and the CLI through the real core). Before this lane the same vendor touched the adapter file + `VENDORS` + `KIND_VENDOR` (src/channel-api.js) + the engine's `apiAccounts` kind list + the egress lists.

**The manual** an agent reads is the declared row: `vibespace-channels api docs <cred>` prints the row's `label`, `docs`, `hosts` and the fence lists (`readByPost`, `sensitive`, the generic sensitive class, the budget).
