# Design: the three "browser" faces (B-d03a — mockups first, then the change)

> Owner, 2026-09-23: *"可能会和其他几个功能产生 confusion"* (it may get confused with several other features); ruling *"先出渲染稿再改"* (render the mockups first, then change). This is a **design document only, zero product code**: three directions rendered as real HTML (`docs/mockups/browser-faces/`) under the product's own class names and theme variables, screenshot in headless Chrome and verified **by pixel**, then scored against six criteria. §5 is the recommendation with a per-file change list; what needs the owner's decision is in §5.3. Chinese original: `docs/design-browser-faces.zh.md`.

**Reproduce:** `node docs/mockups/browser-faces/build.mjs` (emits three standalone `direction-a|b|c.html`; the product rules are copied from `public/style.css` · `chat.css` · `viewers.css` into each file's own `<style>`, dark values; `?view=phone` = the 390 px variant; `?lang=en|ja` swaps the labels) → `node docs/mockups/browser-faces/shoot.mjs` (headless Chrome over raw CDP, `file://`, per direction × desktop zh / en / ja + phone zh = 12 PNGs, each with a JSON beside it: the box of every `[data-face]` entry and its pixel verdict — **≥ 30 light pixels AND ≥ 4 distinct colours inside the box, or it did not render**; the same verdict run on an empty patch of the workspace must come back **red**, else the whole run is refused). The run this document cites: `docs/mockups/browser-faces/index.json` (12/12 green, controls 12/12 unpainted).

## 2. The confusions a user actually hits (each named from the code)

1. **One globe, three meanings.** Toolbar `#btn-browser` (the `UI_ICONS.web` shape) opens the iframe; the rail's `RAIL_ICONS.browser` (the same globe on a 24-grid) opens the Browser profiles **window**; ⚙ Tools ▸ "Browser profiles…" uses `UI_ICONS.globe`; the status-bar chip `chat-status-browser` draws `UI_ICONS.web` before the agent's **last-used profile name**; the Apps catalog's `category:'browser'` card uses `FILE_ICONS.web`. So the globe means "your web view" on the toolbar, "the agent's browser" everywhere else, and "a real Chromium" under Apps. Three faces, three window types (`browser` / `browser-live` / `desktop-app`), one icon.
2. **The toolbar's "Browser" vs the rail's "Browser profiles" vs the Apps dialog.** Three entries within 300 px of each other on screen (toolbar right / rail bottom / toolbar right), all named browser, opening three entirely different things; the rail item came in 2.369.145 on the owner's "this menu is buried too deep" and pushed the agent-browser face onto the same visual tier as the web view.
3. **That "Browser" chip in the chat status bar.** The code has **one** browser chip in the status bar (`chip('browser', …)`, `chat-status-bar.js:704`): a globe + a profile name ("Shopping"); in the same window the live view's toolbar carries a **second globe button** (`browser-live-window.js:133`, "Open this URL in the embedded browser") — which opens the **web view**. What the user sees is "two globes, one opens the agent's live view, one opens an iframe"; the chip's dropdown row "Open live view" and the button's tooltip never point at each other. (If the owner means two other chips, name them in §5.3 D6.)
4. **Two adjacent rows in the ⚙ tree.** Tools ▸ Desktop apps… (30) and Browser profiles… (35) sit next to each other; the web view has **no row** in the ⚙ tree at all (only the toolbar button, the phone sheet, the command palette). Somebody looking to "open a browser" in ⚙ finds only the other two faces.
5. **The Settings category "Browser" is only about the agent browser.** The 12 rows at `settings-schema.js:413-517` (`browser.isolateSessions` … `browser.defaultProfile`, `window.realDesktopTargets`) are all agent browser / window targets; "Show Browser button" (`toolbar.showBrowserButton`) sits under Toolbar and means the **web view**; the Apps dialog's "Agents on your real desktop" hint says "Off — turn it on in Settings → Browser" (`desktop-app-launcher.js:292`). Three "Browser"s, three referents.
6. **Window titles and the taskbar.** A web view window is titled by hostname or 'Browser' (`browser-window.js:12-13`); a live view by the profile name; a desktop app by its label ("Chromium"). The taskbar shows three "browser" things under three glyphs (globe / window-with-dot / window) and only `browser-live` says "Browser (live)" in its subtitle.
7. **The phone is asymmetric.** The "+" sheet has only the web view row ("Browser"); the agent browser is reachable only by long-pressing a session card → "Live browser view"; desktop apps have **no** phone entry (`mobile-nav.js:60-68`) — right after 2.369.158 made a desktop app on a phone "the whole app scaled to fit and clickable".

## 3. The three directions (real HTML, `docs/mockups/browser-faces/`)

Each direction = one standalone `direction-x.html` (product rules inlined) + desktop 1200×800 (zh / en / ja) + phone 390×844 (zh) PNGs + a JSON beside each. One fixture for all three: a claude session comparing prices on profile "Shopping", the third vendor needs a login; a real Chromium running on xpra; an example.com page. The yellow circles are **annotations** (hidden on the phone), not product elements.

### A — one "Browser" hub entry, three cards (`direction-a.html`)
The toolbar, the rail and ⚙ Tools ▸ each keep **one** entry (the globe stays) and all open a `createModalShell` dialog `dialog.browser-hub`: an intro line ("three things are called a browser — pick by who drives it") + three cards (`browser-hub-card`, on `.desktop-launch-card`'s type and spacing): **Web view** (you · URL field + Open), **Agent browser** (the agent · Live view / Profiles… / "1 session live"), **Browser app** (you · Chromium / Firefox / "via xpra"); each card carries a "what it is NOT" line; a "Running" section below lists everything alive of all three kinds (Shopping · agent is driving / Chromium · xpra). Phone: the hub becomes a bottom sheet, the three cards stacked. The Apps button is untouched (it still owns xterm / editors).
*Screenshot facts:* the toolbar entry is 72 / 79 / 83 px (zh / en / ja) — the same width as today's Browser button; the cards are 223 px wide and 195 / 190 / 221 px tall (ja is the longest copy; no in-dialog scrolling); on the 390 px phone each card is ~150 px and "Running" is still on the first screen.

### B — rename the faces, keep three entries (`direction-b.html`)
The names say who drives it: toolbar **Web view** (网页视图 / ウェブビュー; the globe is **only** hers now); the rail item + ⚙ Tools ▸ + the status chip become **Agent browser** (Agent 浏览器 / エージェントブラウザ) with the `browser-live` window type's "window with a dot" glyph (the rail on a 24-grid version, proposed here); the Chromium card under Desktop apps is labelled **Browser app** (浏览器应用 / ブラウザアプリ) and its window title says "Chromium — Browser app". The ⚙ tree stays Tools ▸ Usage… · Background Work… · Desktop apps… · **Agent browser…** · Plugins…. The phone "+" sheet gains the missing rows: Web view / Desktop app… / Agent browser.
*Screenshot facts:* the toolbar "Web view" is 83 / 86 / **105** px (ja is the widest button on the bar, still narrower than "新規セッション" at 113 px); the status chip grows from "🌐 Shopping" to "▣ Agent browser · Shopping" (~70 px more; `$0.42` still fits in a 470 px window); the ⚙ flyout's five rows do not wrap.

### C — fold the web view into the browser app, two faces (`direction-c.html`)
Only **one** "Browser" button for you: with a display backend it is a real Chromium on this machine (xpra; title "Chromium — Browser"; glyph = a globe inside the app window, a new SVG proposed here); **without** one the same button frames the page inside the window (URL bar + proxy) — the old web view becomes this window's **fallback rung**, not a face. The other face is the agent's (rail + ⚙ "Agent browser", live view + take over). The Apps catalog stays; its Chromium card and the toolbar button are the same thing. The phone "+" sheet has two rows: Browser / Agent browser.
*Screenshot facts:* the toolbar button is 72 / 79 / 83 px; the fallback note is one line at the window's foot (zh wraps to two; the label is nowrap); on the phone the real Chromium's picture is fit-scaled per 2.369.158.

## 4. The six criteria and the scores (5 = nothing to fix, 3 = works with a visible cost, 1 = fails)

| Criterion | What was measured | A hub | B rename | C fold |
|---|---|---|---|---|
| **Discoverability** | how many steps somebody who "wants a browser" needs to reach the right face; entry count | **5** — one entry; the hub explains the three faces itself; "Running" merges the three kinds | 3 — three entries remain, told apart by name; you must know which one you want first | 4 — two entries; the human one is simply "Browser" |
| **Naming honesty** | name = what it does; same name same thing, different name different thing | 4 — the cards are honest; the toolbar word "Browser" is still three-valued until the hub opens | **5** — every entry says who drives it and what it is; the globe has one meaning left | 3 — "Browser" hides a ladder: with a backend a real Chromium (tabs / logins), without one an iframe — one word, two experiences, varying by machine |
| **Phone parity** | on 390 px every face has an entry and works | **5** — one sheet, three cards (today the phone has no desktop-app entry and reaches the agent browser only by long-press) | 4 — all three rows in the "+" sheet; the "Agent browser" row is session-scoped, so without a session context it must open a session picker first | 3 — the xpra picture is usable on a phone but small; what most phone cases really want is the iframe, and that now depends on "does the machine have a backend" |
| **i18n length** | the toolbar button, the ⚙ row, the rail tip, the status chip in zh / en / ja, in px | **5** — 72 / 79 / 83 px, same as today | 3 — "Web view" 83 / 86 / 105 px (ja the widest); "Agent 浏览器" is mixed-script; the chip +70 px | 4 — toolbar unchanged; "Agent browser" only on the rail tip and the ⚙ row |
| **Migration cost** | new components, files touched, i18n keys, data/layout migration, dependence on a parallel lane | 2 — a new dialog + "Running" must aggregate three sources (live `browser` windows / the profile digest / the desktop-apps list) + ~20 i18n keys + the toolbar/rail/⚙ rewired; no data migration | **5** — labels and icons only: ~13 files, ~14 i18n keys, zero new components, zero data migration (§5.2) | 1 — depends on B-bfe6 shipping + a display backend on the machine; `openBrowser(url)`'s 8 callers must hand a URL to the Chromium inside xpra (launch args yes; **later navigations** need CDP or `xdg-open` — no channel exists); the `browser` windows and the `proxy` flag in layouts.json are either migrated or the fallback rung is kept forever (not one line less code) |
| **What breaks** | muscle memory, existing callers, layout replay, suite pins | 3 — the toolbar globe no longer opens a page directly (one more click); the command `browser.open`, the Ports Open rows, published pages and the live view's hand-off must **keep opening the web view directly**, not the hub; layout replay unchanged | **5** — zero structural change; window type ids, openSpec actions, settings keys, the rail id all stay; only the suites pinning labels follow (`test-contributions`, `test-browser-housekeeping`, `test-profile-blindness`, `test-ax-paint`'s title/aria-label census) | 2 — `setup-flows.js:555` opens a generated HTML blob URL (a Chromium inside xpra cannot open this page's blob); the Ports panel's "Open (through the app proxy)" loses its proxy semantics; which rung an old layout's `browser` window replays into depends on the machine's state at the time |
| **Total** | | 24 | **25** | 17 |

## 5. Recommendation

### 5.1 The verdict

> **SHIPPED (B), 2.369.168** (2026-09-24, owner: "那就选B吧"; the third chunk of the browser takeover — `docs/design-browser-takeover.zh.md` §7 / D10, §5.3's D1–D7 all at this document's defaults). Labels and icons only: the toolbar says **Web view** (the globe is its alone); the rail item + ⚙ Tools ▸ **Agent browser…** (order 35) + the status-bar chip "**Agent browser · <profile>**" (the tooltip's first line carries the same prefix) + the card's three commands + the Session Properties section + the Settings category **Agent browser** (Services group) all move to the `browser-live` "window with a dot" (`UI_ICONS.browserLive`, defined once in `icons.js`; the rail's 24-grid variant is `RAIL_ICONS.browser`); the live view's kind label is **Agent browser (live)** and its hand-off button says "Open this URL in a web view"; the Apps dialog's intro adds "the agent cannot reach it", and a catalog card's sub-label is prefixed **Browser app ·** gated on `row.browser` and shown on a STARTABLE card (live with B-bfe6's Browsers section, merged at integration — D7 decided there; a dimmed browser card keeps only its short reason); the phone "+" sheet gains Web view / Desktop app… / Agent browser (the last: the active window's session's live view when it holds a browser; else a picker over the live sessions holding one; none ⇒ the Agent browser window). No window-type id, openSpec action, settings key or rail id changed; layout replay is unaffected. The session card's menu renders text rows only (`showContextMenu` draws no `icon`), so the card menu carries the NAME, not the glyph. Gates: `test-browser-faces` (new, fast) + `test-window-types` / `test-contributions` / `test-ax-paint` (rail items gain `aria-label`) / `test-browser-housekeeping` / `test-profile-blindness(-chip)` / `test-architecture` §53 (the glyph defined once) / `test-mobile-gaps`.

**Do B, now.** It removes confusions 1 / 2 / 3 / 5 / 6 of §2 outright (one globe, one meaning; three names, three things; the Settings category and the hint follow the rename) and covers 4 / 7 through B's three phone rows and the renamed ⚙ row; zero structural change, zero migration, one commit. Borrow **two** things from A: the Apps dialog's intro gains the "who drives it" sentence and the Chromium card's sub-label says "Browser app"; the phone "+" sheet gets its three rows. **Not C now**: it is the question worth asking only **after** B-bfe6 lands and xpra is common in the fleet ("should the web view remain a face at all") — by then B has straightened the names and C is merely one entry fewer. A's hub can still return after B as **the phone sheet's form**; the desktop does not need it.

### 5.3 What needs the owner's decision
- **D1 The names.** This document uses Web view / Agent browser / Browser app (zh 网页视图 / Agent 浏览器 / 浏览器应用; ja ウェブビュー / エージェントブラウザ / ブラウザアプリ). Alternatives: "Embedded page" (plainer, longer), "Page" (too generic); whether "Agent 浏览器" should be pure Chinese 代理浏览器 (not recommended — the product never translates "agent").
- **D2 Renaming the Settings category.** `Browser` → `Agent browser` changes the visible category name in the Services group and settings search; leaving it keeps §2.5.
- **D3 The rail glyph.** Swap to the "window with a dot" (consistent with the `browser-live` window and the taskbar) or keep the globe and only change the tip? Recommended: swap — the globe belonging to the web view alone is B's pivot.
- **D4 Is C the end state?** If the owner rules "the iframe should not be a face", C is scheduled after B-bfe6 ships (prerequisites: a URL hand-off channel + the fallback rung on backend-less machines + a layout migration); otherwise B is the end state.
- **D5 The phone sheet.** Add all three rows (recommended) or rename only (minimal).
- **D6 "The two Browser chips".** §2.3 finds, from the code, ONE status-bar chip plus the live view toolbar's globe button; if the owner means two other places, name them and the table is corrected.
- **D7 Ownership of the browser card in the Apps dialog.** The B-bfe6 lane owns the registry rows; whether the "Browser app ·" sub-label lands in its commit or in B's is decided once, at merge.
