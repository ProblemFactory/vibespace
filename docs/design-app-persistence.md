# App persistence — apps a user (or their agent) installs survive a pod recreation

2026-09-27 · **design; owner decisions D1–D6 answered; the MUST + SHOULD probes of §5 were run on a test instance (2026-09-27)** · English twin of `design-app-persistence.zh.md` (the Chinese file is authoritative; this one is a faithful condensation). Review method: four independent proposals (persistent overlay / chroot app system / Nix on the PVC / manifest replay) scored by three independent judges on one rubric, with every factual claim checked. **Public-repo rule: zero cluster detail** — placeholders only (`<registry>`, `<domain>`, `<storage-class>`).

## §0 One paragraph

**Recommendation: one product-owned package manifest + a local .deb cache + a one-click human gate as the spine (every pod, no image or chart change), and on pods that have the mount capability a persistent "app system" — a small same-release Linux userland on the PVC where apt installs land for good: zero replay at boot, untouched by image upgrades.** The user tells their agent "install GIMP"; the agent can only PROPOSE; the user sees "Install GIMP? 612 MB" in the For you tray, clicks Install, the log streams, the app appears in Desktop apps and the agent may open it by id. After a pod recreation: a pod with an app system reinstalls NOTHING; a pod without the capability degrades to "server up first, then an offline reinstall from the cache in the background, rows read restoring…". Data was never at risk: HOME is the PVC.

The SteamDeck-style "immutable image + persistent overlay upper" is unanimously NOT recommended as the source of truth: it is the only design that can make a pod fail to boot (DNS/sudo broken by user data), it ties every image rebuild to a fleet-wide reinstall, and it sits at the kernel's overlay stacking-depth limit; its one advantage (raw `sudo apt` persists) is exactly what nobody wants — nothing knows what was installed. Its operational lessons are absorbed (§3.7). Nix is the least-privilege runner-up but a second ecosystem per user (2–3 GB per big app, GL/fonts wiring); not built, kept as an optional no-capability tier for CLI tools later.

## §1 Facts (read from the code)

- The only thing that survives a pod recreation is the HOME PVC (RWO, 100Gi thin by default, `Recreate` strategy). The container rootfs — /usr, /etc, /opt, /var/lib/dpkg, everything `sudo apt` installed — is lost every time.
- VibeSpace is baked into the image and copied into the PVC at first boot; it runs and self-updates from `~/vibespace` (`deploy/docker/Dockerfile`, `entrypoint.sh`).
- The container user is uid 1000 with passwordless sudo (root-equivalent inside its own pod); the container starts as root and drops with `runuser`.
- CAP_SYS_ADMIN + AppArmor Unconfined are granted when `fuse.enabled` or `cephfs.mons` is set (conditional; the chart defaults grant neither); `/dev/fuse` via a device plugin; no privileged, no loop devices, no user-namespace setting, no seccomp profile set.
- The pod ALREADY performs kernel mounts from inside (`sudo -n mount -t ceph`, rclone FUSE, tailscaled) — `mount(2)` works where SYS_ADMIN is granted: a proven fact, not a hope.
- Today's only persistence convention for system packages is `~/.vibespace-init.sh`, replayed synchronously at every boot before node starts (liveness allows ~5.5 min); no product code manages it.
- Existing install doors: the xpra install plan (plan first → `sudo -n sh -c` → setsid-detached with a pidfile slot + flock → streamed log → re-attached, never run twice) and the plugin system's boot replay (intent in `data/plugins.json`, binaries on the PVC).
- Agent tool pattern: static `data/bin/vibespace-*` CLIs, `VIBESPACE_API` + `vsst_` token → `/api/agent/*`; the human gate is one For-you item + cookie-only routes (agent bearers 403). The desktop-app catalog is code-fixed and "an exec is a human's" (agents open catalog ids only).
- **Settled by probe P1 (2026-09-27, measured on a test instance's pod; every fleet pod runs the same image digest):**
  - Base: **Debian 12 (bookworm) amd64** — the repo Dockerfile's line (`node:22-bookworm-slim`): **Node 22**, **TigerVNC 1.12 + XFCE 4.18 + Debian's chromium** (a real deb, no snap stub). The private deployment notes' Ubuntu 24.04 + KasmVNC + Node 20 + git-clone-at-first-boot was an early design that never shipped; the first boot seeds the app offline with `cp -a` from the image. The fleet container user is renamed to the instance name at boot (`/home/vibe` stays as a compat symlink).
  - **xpra is NOT in the image the fleet runs today** (nor xdotool, Xvfb): the image predates the Dockerfile's xpra line — the desktop-app xpra rung on fleet pods needs a new image or the in-product "Install xpra" (onto the ephemeral rootfs — exactly what Layer 0 exists for).
  - `uv` is not in the image (the `uv tool` kind of §3 first installs uv into `~/.local/bin`).
  - Privileges: `capabilities.add: [SYS_ADMIN, NET_ADMIN]`, AppArmor Unconfined, **no seccomp filter at all** (`Seccomp: 0`), NoNewPrivs 0; bounding set = the runtime's default 14 + those two, SYS_CHROOT included, **SYS_PTRACE absent** (root cannot read a uid-1000 process's smaps/environ; a setuid bwrap cannot work). Every fleet pod has them (fuse and cephfs are both on in production).
  - HOME: **ext4 on a block PVC, `rw,relatime` (no nosuid/noexec)**; the PVC root is `root:<user> 2775` through fsGroup (setgid — directories mkdir'd below it inherit the group and setgid, §5 P3). `/tmp` lives on the container's overlay root; `/dev/shm` is 64 MiB.
  - Kernel 6.x (the node distribution's kernel); `apparmor_restrict_unprivileged_userns=1`, yet `unshare -Ur` works for the pod user. pid 1 is `runuser` (no init) and never reaps orphans (harmless zombies; the keeper is its own shim's parent and reaps it).

All three judges: no single road suffices; ②'s execution model on ④'s record layer beats every single approach (judges 1 and 2 explicitly; judge 3 chose ① as a disposable cache over ④, for the same reason — ④ is the source of truth). Adopted: ② + ④, with ①'s operational lessons (§3.7). Factual errors the judges caught and this document corrects: in this pod (init user namespace + SYS_ADMIN + AppArmor Unconfined) a fresh `mount -t proc` is NOT refused — the app system still rbinds /proc to inherit the container's masks; an overlay's workdir is written at every mount, so a full PVC yields a read-only mount or ENOSPC, never "mounts anyway"; `bwrap` as root needs no user namespace (measured on this box), so flatpak via a setuid bwrap is a probe, not a known failure (P16: on a fleet pod a setuid bwrap fails — no SYS_PTRACE; only a pivot_root + fresh-proc entry runs it, §5); the image ships `dbus-x11`, so GTK dconf writes most likely persist through `dbus-launch --autolaunch`; setuid effectiveness follows the mount the exec path traverses, not the PVC's nosuid.

## §3 The recommended design: three layers, one manifest, one gate

**Layer 0 — manifest, cache, gate (every pod; build first; ships by `git pull`).** `~/.vibespace/apps/manifest.json` (the server is its one writer): sources (https only, key sha256-pinned), entries (`apt` | `uv-tool` | `npm` | `appimage`; who asked, why, approved when; catalog rows; services), resolved versions. `~/.vibespace/apps/debs/` = a sha256-indexed local `file:` repository (`.deb` + stanza + `Packages`). Two rules measured by P15: `Keep-Downloaded-Packages` keeps only what apt fetched THIS time — on a drifted rootfs (the product's own xpra install) dependencies go missing, so completeness is judged against the image's base package list (closure − base ⊆ cache, topped up with `apt-get download`); and apt's `_apt` sandbox user cannot traverse `~/.vibespace` (0700), so the `file:` rung passes `-o APT::Sandbox::User=root` (or uses a path `_apt` can reach). ONE package slot per machine (the xpra INSTALL_LAUNCHER/RUNNER generalised; flock; xpra install, app install/remove/refresh and the boot replay all take it; every apt call passes `DPkg::Lock::Timeout=300`). The plan is PURE and runs nothing as root before approval (`apt-get -s` + `--print-uris` as the user → closure, sizes, new sources, fingerprints; refusals by name: `needs_snap`, `conflict` (the WHOLE manifest is simulated), `bad_name`, `bad_source`, `no_sudo`, `no_apt`). The install runs the approved script detached through the slot with names as positional argv; the server parses `= delta / = desktop / = service` lines into the manifest and catalog rows (`app.<entry>`, `.desktop` Name/Exec/Icon, field codes dropped, validated). Agent flow: `vibespace-app search|install|remove|status|wait|docs` (all pre-approved — none executes anything; `add --kind uv|npm|appimage` is HELD like `vibespace-job run`); the outcome reaches the agent free on its next turn. Human gate: ONE For-you item (new origin `apps`) → the same dialog component as "Install xpra on {machine}…" (commands, packages, new sources + fingerprints, sizes, "after a pod restart: …") → Install streams the log. Approving an install approves its `.desktop` rows, so `vibespace-window open app.gimp` is allowed (the "an exec is a human's" rule stays for arbitrary executables). **Who installs (owner D3, 2026-09-27):** installing an app is not a frequent need, so ordinary sessions get ZERO new injected teaching text — `vibespace-app` is just a binary on PATH and its manual lives only in the on-demand `vibespace-docs` index (`vibespace-docs apps`); the primary door is the user's own "Install an app…" in the Desktop apps dialog; a "Let an agent help" button there spawns a TEMPORARY helper session through the existing new-session-with-a-prefilled-prompt path (the request + the full apps manual + the machine's facts as its first prompt; it proposes, the user approves in the same dialog, it says done, it is archived as a helper). Approved catalog rows are openable by id by every agent (no context cost — `vibespace-window` already exists). **Manual .deb (owner D4):** "Install from a .deb file…" — plan = `dpkg-deb -I` + `apt-get -s install ./file.deb`, the same gate, `apt-get install ./file.deb`, the file copied into the local repository with its sha256 so replay/Rebase can reinstall it. A drift tripwire (`DPkg::Post-Invoke`) labels packages installed outside VibeSpace "lost at the next pod restart — [Adopt]"; `~/.vibespace-init.sh` remains the escape hatch with a one-time "move these apt lines to Apps" offer. Free-space floor: refuse below installed + 2 GiB.

**Layer 1 — the app system (pods with SYS_ADMIN; the recommended persistent tier).** `~/.vibespace/sysroot/rootfs/` (root:root, a same-release minbase with its own /usr /etc /var/lib/dpkg), an identity file (`codename/id/arch/createdFrom/helperContract`), user-owned exported launchers in `~/.vibespace/sysroot/bin/` appended to the END of PATH. Two small files are re-installed onto the ephemeral rootfs at every boot (`sudo -n install`, the `/sbin/modprobe` shim precedent; only when the chart sets `VIBESPACE_APP_SYSTEM`): the helper `vs-sysroot-enter` and a sudoers drop-in (`visudo -cf` before install) that grants NOTHING new — it makes sudo direct-exec the helper on the same pid with the X env kept. The helper: derive HOME from `SUDO_UID` (never from the environment), refuse unless `realpath(R)==R`, root-owned (uid 0 and not world-writable; the group is NOT required to be root — fsGroup rewrites it), identity present, arch matches (reference implementation: `deploy/sysroot/vs-sysroot-enter`, the one that passed the §5 probes); `unshare --mount --propagation private`; rbind /proc /sys(ro) /dev /home /tmp /run/user/$UID, ro-bind `/etc/{resolv.conf,hosts,hostname,localtime}` and the image's `/usr/share/fonts`; upsert the user's passwd/group line; `chroot --userspec` + `env -i` allowlist (no session token, no host `~/.local/bin`); `--root` only for apt/dpkg, only by the server. The namespace dies with its last process — nothing to unmount, no stale mounts. A shim is `exec sudo -n <helper> --cwd "$PWD" -- /usr/bin/gimp "$@"`; every hop is an exec on the keeper's pid, so handle / starttime / group kill / marker / PSS report are unchanged (probe P7 must prove the direct exec). Boot: nothing before listen; after listen ≈ 0.3–0.6 s in child processes (the two files — measured 35 ms, identity + manifest, shim regeneration, `dpkg --audit` → "An install was interrupted — Repair"). Creation once, on a human click: rung A (a minbase tarball baked into the image, 15–60 s offline) or rung B (`debootstrap`, measured 23 s / 206 MB; the target directory is created `root:root 0755` with setgid cleared first, or fsGroup's group + setgid leak into the whole userland — §5 P3). Each app launch pays ≈ 75 ms (measured, the bash reference: 47 external commands + the rbinds; a compiled helper would reach 20–40 ms). Image upgrades: the two package worlds never share a dpkg database, so "dpkg state over a changed base" cannot happen; a release change keeps the old app system running (X11/GLX are wire protocols) and shows "Rebase…" (build `rootfs.next`, replay the manifest, verify exports, swap, keep `rootfs.prev` for Roll back); an arch change refuses + Rebase. Security updates no longer come from the image: a per-user "N updates · last refreshed N days ago" chip + Refresh, and a per-pod fleet lever for the operator (`runuser -u <u> -- vibespace-app refresh --all`) — the design's biggest ops gap, stated. GUI: launched like any registry exec (DISPLAY/XAUTHORITY through env_keep + the allowlist, X via the /tmp rbind, GL = the app system's own llvmpipe, fonts via the ro-bind, dbus via autolaunch).

**Layer 2 — replay (pods without the mount capability; the same manifest).** After listen: read the manifest → read the ephemeral marker `/var/lib/vibespace/apps-replayed` (a server restart hits it in 1 ms) → on a fresh rootfs launch the detached runner through the slot: restore sources/keys/pins → rung 1 OFFLINE from the local repository (measured by P15: GIMP = 117 packages / 92 MB / 397 MB in 8.9 s offline, ~1 s for a few small packages — dpkg unpacking dominates, the same set online took 9.9 s) → rung 2 online only when the base moved / rung 1 failed / Refresh → failures named per entry (state.json + one notice), never blocking others. Rows read `restoring…` meanwhile; jobs marked `after: apps` wait. A pod killed mid-replay is harmless (a fresh rootfs next time).

**User-level kinds** (no replay in either layer): `uv tool` (uv-managed Python), `npm --prefix ~/.local` (rebuilt on a node ABI change), AppImages extracted once into `~/.local/opt/<id>`. Recorded in the manifest; HELD CLI card only, no For-you approval (they grant nothing the agent's Bash lacks).

**Service packages (v1 boundary):** postinst completes without systemd, nothing restarts them; the manifest records units; the user runs them as `vibespace-job run --keep-up` marked `after: apps`; a "persist these paths" field is v2.

**Catalog:** `DEFAULT_REGISTRY` ∪ manifest rows (`app.<entry>` / `sys.<name>`); icons through a cookie-only route (`img.src`, nosniff); greyed rows carry their reason (restoring / unavailable: needs the pod's mount permission / interrupted — Repair); an "installed outside VibeSpace" column with Adopt.

**§3.7 Rules absorbed from the overlay proposal** (true for any persistent tier on a boot path): bake an image stamp (`/usr/share/vibespace/image.json` + `base-packages.tsv`) so "the base moved" is a fact; boot-path scripts exec from the image or the checkout, never from the PVC; anything before listen needs a smoke test + attempt counter + safe mode (this design puts everything after listen); anything covering /etc must save-and-rebind resolv.conf/hosts/hostname; a PVC restore may trip fsGroup's `OnRootMismatch` walk (gid + group bits change, uid stays, setuid re-applied) — the helper judges by the identity file, not root ownership, and repairs drift with `--reinstall` from the cache.

## §4 Not now / later
Overlay as the source of truth: no (boot-failure class, fleet-wide reinstall per image, stacking-depth EINVAL, xattr-sensitive backups). Overlay as a disposable cache: not v1 (the app system already has zero replay). Nix: not v1, optional later for CLI tools on capability-less pods. flatpak: probe P16 decides (setuid bwrap). Paired Linux machines get the manifest + catalog rows for free (their rootfs persists; no app system needed).

## §8 Risks, stated
Two userlands confuse people (terminal `sudo apt` is ephemeral, `vibespace-app` persists; an IDE in the app system sees its own toolchain) — the tripwire + Adopt + the first line of the agent manual. Patch ownership moves to the user (§3). The app system shares the PVC with `data/`. Layer 2's boot latency exists only on capability-less pods and only after listen. The kernel is shared (no DKMS/modules) and there is no GPU (GL = llvmpipe).
