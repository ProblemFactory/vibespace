# Design: the For-you inbox — reply, running dot, per-window mini inbox, usage UX (design-user-inbox-reply, 2026-09-23)

> Owner (verbatim, Chinese): "实际上现在inbox功能被利用的很少，原因是agent经常大量发inbox，然后我做为用户也没有什么方便的方法快速针对一个inbox message给出响应，而只能markdone和叉掉，建议 1. 给inbox item一个回复按钮，我可以直接回复某个inbox item，然后会自动变成消息发给这个agent（如果agent没在运行回复按钮就是灰色禁用并给tooltip，并且在inbox里这个agent的标题的地方用一个小点标记这个agent是否在运行。2. 在窗口标题栏同样增加一个mini inbox，只展示这个窗口对应的agent发送的消息，其他行为一致。3. 你可以思考下其他可能的UX改进增加使用率。" — the inbox is barely used: agents flood it, and the only answers a user has are "done" and "dismiss"; (1) a Reply button per item that becomes a message to that agent (disabled with a tooltip when the agent is not running; a small dot on the agent's group title says whether it runs); (2) the same as a mini inbox in each window's title bar, showing only that agent's items; (3) think about other usage-raising UX.
> The owner's quoting rule (verbatim): "注意回复inbox item的时候 发给agent的消息得带有对应的引用信息" — a reply to an inbox item must carry the item's quote when it reaches the agent.
> Chinese twin: docs/design-user-inbox-reply.zh.md. Version 2.369.169 (ONE CHANGELOG entry, appended chunk by chunk).

## §0 In one paragraph

A For-you item gets a **reply box**: what you type on the item travels **the same server path the chat composer uses** (never the delivery ladder, never the spend authorizer — it is your own typing), prefixed with a **quote block** of the item (a stable first line `[For you reply #<id>]`, when it was filed, the full text, the first 1500 chars of the detail) so the agent knows exactly which ask it answers; a successful send resolves the item (`resolvedBy: 'reply'`) and keeps the reply on it ("You replied: …"). Agent not running ⇒ the button is disabled with a tooltip; each agent's group head carries a **running dot** (filled green = mid-turn, hollow green = live and idle, amber = paused on you, grey = not running) drawn from the `active-sessions` payload the client already holds (one new column `turn`, derived server-side once a second — never a new poll). Every chat window's title bar gets a **mini inbox** badge (the count of that session's open items, hidden at 0) opening a popover that reuses the ONE row renderer. Usage-raising: **option chips** (`vibespace-ask --options "A|B|C"` ⇒ one-click reply with the label), **inline one-line reply**, **decisions-first ordering**, **flood folding + per-agent "mark all seen"** and a **board-state chip** are built now; the rest (auto-resolve on typing, expiry from dead sessions, j/k/r/d, per-agent mute, stash-for-next-turn, terminal-mode replies) is listed as future.

## §1 Facts (read-only, from the code)

- **The item** (`src/user-todos.js`): `{id:'ut-'+10hex, sessionKey, text ≤300, detail ≤2000|null, urgency low|normal|high|urgent, kind action|notice, status open|done|dismissed, by, sessionName, jobId, i18n, action, expiresAt, createdAt, resolvedAt, resolvedBy user|agent|system|expired}`; idempotent by (sessionKey, text); 20 open per session (add throws with guidance), 1000 total (resolved pruned first); `snapshot()` = open sorted urgency-then-newest + the last 15 resolved; every change broadcasts `user-todos-updated {todos}`; writes tmp+rename, 500 ms debounce.
- **How an item knows its session**: the agent route `POST /api/agent/user-todo` (vsst_ Bearer; `agentSession(req)` finds the activeSessions entry holding that token) ⇒ `sessionStatusKey(s, id)` = `<backend>:<backendSessionId>`, `webui:<id>` early and rekeyed on the next call. Server producers (spend-guard / login-expiry / channels / jobs) use their own keys: `accounts`, `jobs`, or the owner session's `claude:<cid>`.
- **The panel** (`src/lib/user-todos-panel.js`): `#taskbar-user-todos` segmented badge + `#user-todos-popup` (grouped by session, group head → jump; ✓/✕/↺ → `POST /api/user-todos/:id {status}`; ⤢ viewer; detail behind `<details>`; a Notices section; a recently-resolved tail); the phone entry `#mobile-nav-todos` uses the SAME `renderBtn` / `togglePopup`; while open the row order is APPEND-ONLY (inc-mtw02kbq-kj96, PURE `user-todos-layout.js`: `openLayout/nextLayout/entriesFor`) — but every broadcast still does `popup.innerHTML = …`, a whole re-render. That is exactly what this design must change: a reply box being typed into would not survive one.
- **Live facts the client holds**: the `active-sessions` payload (`activeSessionsPayload()`, server.js): per session `{id, name, backend, backendSessionId, sessionKey, mode, host, remoteState, …LIVE_SESSION_FACTS}`; the sidebar's `_merge()` adds `status:'live'` and `webuiId`. **It carries no turn state**: `_isStreaming` / `_turnState` ride only per-session messages to attached windows — a session without an open window is opaque. `_isStreaming` has 9 write sites in 5 server files (ws-handler / session-stdout / codex-events / acp-events / claude-stream-json): hooking a broadcast on each is a twin-drift nursery.
- **The typing path** (`src/ws-handler.js` case `'chat-input'`): `session.pty && session.mode==='chat'` ⇒ clear the interrupt timer → `adapter.formatChatInput(text, msgId)` (poison guard ⇒ `error code:'input-rejected'`) → the >64 KB frame-file bypass (wrapper capability gate) → `_isStreaming=true`, `_userInputAt` (§22: the owner's own turn), `autoResume.noteRecovered` → the `/compact` label → `pty.write(payload+'\n')` → `feedLive(userMsg)` (every subscriber sees the user bubble at once) → the 5 s stdin-ack heal. **Mid-turn is the same path**: the frame is written and the CLI/wrapper queues it itself (claude = the CLI's own queue; codex = `thread/queue/add`, `queue_changed` published to the queue strip). This is the only path that is "exactly as if you typed" — the delivery ladder (`conversation-deliver.js`) is "somebody else's message" (peer card, spend authorizer, stash), not this.
- **The money census**: `scripts/test-spend-paths.mjs §2` censuses primitives such as `formatChatInput(` PER SITE; the ws-handler site is excused by an `ALLOW` row ("THE HUMAN PATH"). ws-handler holds **exactly one** `formatChatInput` ⇒ once it moves, that row must be **re-pointed**, or "no dead allowlist entry" goes red.
- **The human-only route pattern**: `src/routes/reset-credit.js` — `isAgentBearer(req)` (vsst_/jbt_) ⇒ `403 agent_forbidden`; cookie auth comes from `auth.middleware` on every non-`/api/agent/*` route.
- **Reusable chrome**: `createPopover(anchor, cls, opts)` sets `data-popover` (the global layered Esc); `createModalShell`; `UI_ICONS`; the title bar's `setOwnerBadge(id, badge)` = the keyed title-bar badge precedent (a sibling after titleSpan; drawn on the tab by `_renderTabBar` when grouped); ≤768px `.usage-popup` becomes a full-width sheet and `#user-todos-popup .ut-act` is already lifted to 36 px.

## §2 D1 Reply semantics (decisions with defaults)

**D1.1 The path is the typing path, as ONE implementation.** Extract the body of the ws `'chat-input'` case into `src/server/user-input.js` `createUserInputSender(deps)` → `send(sessionId, text, {msgId, origin}) → {ok:true, msgId} | {ok:false, code, error}`; server.js constructs it (it already holds every dep: activeSessions / adapterRegistry / BUFFERS_DIR / broadcastToSession / feedLive / autoResume / reattachLocalPty / ptyQuietSince) and hands it to ws-handler through ctx (`WS_CTX_CONTRACT` +1 key `sendUserInput`, all three faces in one commit: contract / destructure / call site — pinned by test-ws-contract) and to the reply route. The ws case becomes thin: `const r = sendUserInput(...)`; only `input-rejected` / `too_large` still map to today's `{type:'error', code:'input-rejected'}` frame, no-session / not-chat stay a silent `break` (behaviour byte-identical). A reply goes through **neither** the spend authorizer (a per-occurrence owner action, D6's "typed turns are never counted") **nor** the delivery ladder; the spend census `ALLOW` row moves from `src/ws-handler.js#user-frame` to `src/server/user-input.js#user-frame`, its why kept ("THE HUMAN PATH") plus "the reply route is the second caller of the same function". The route file composes no frame ⇒ no second site in the census.

**D1.2 The text the agent receives (the owner's quoting rule).** PURE `src/inbox-reply.js` (CJS, imports nothing, bundled) `composeReply(item, replyText, {now})`:

```
[For you reply #ut-3f9a1c2b7d]
> filed 12 min ago (2026-09-23 06:02 UTC) · urgency high
> Approve the migration plan before I continue
> detail:
> Options: A) run now  B) wait for tonight's backup. I recommend B.
> options: run now | wait for backup
> … (detail cut at 1500 of 1987 chars — `vibespace-ask list` prints the whole item)

wait for backup — and tell me when it is done.
```

- Line 1 **verbatim** `[For you reply #<id>]` (English, a protocol value, never i18n'd — agent-facing text is not translated, and English greps best); regex `^\[For you reply #(ut-[0-9a-f]{10})\]$`.
- The quote block, every line prefixed `> `: line 1 the filing instant (relative + absolute UTC) and the urgency; then the whole `text` (≤300); with a `detail`: `> detail:` then the detail line by line, **the first `DETAIL_QUOTE_CAP = 1500` chars only**, a cut appends one line `> … (detail cut at 1500 of N chars — …)` (absent when nothing was cut); with `options`: `> options: A | B | C`. A server producer's i18n item quotes its English `text`/`detail` (the store's dedupe key = the agent's contract).
- A blank line, then the reply verbatim (`REPLY_MAX = 4000` chars, CRLF normalised; longer ⇒ 400 `too_long`, blank ⇒ 400 `empty`). An option chip's reply is the label itself.
- `parseReply(text) → {id, quote, reply} | null` is the inverse (the renderer and the manual share it); `composeReply` and `parseReply` are each other's fixture (round-trip table + hostile strings pass through verbatim — this is text, not HTML).
- The whole frame is < 6 KB, never near the 64 KB frame-file gate; the shared sender handles it anyway.

**D1.3 What the agent sees.** `docs/agent/ask-manual.md` gains `## Replies from the inbox`: the first-line shape, every quote line, the cut marker, the `options` line, "the reply may be exactly one of your labels"; the agent route's teaching block (`agent-routes.js` ~1697) gains only `[--options "A|B|C"]` and one sentence "the user can reply from the inbox: the message opens with `[For you reply #<id>]`". Phone and desktop identical.

**D1.4 The item after a reply.** Route order: verdict → send → only on success `userTodos.resolveByReply(id, text)`: `status:'done'`, `resolvedBy:'reply'`, `reply:{text ≤4000, at}` (new field; an already resolved/dismissed item **also accepts a reply** — a reply is refused for delivery reasons only, never bookkeeping: then the existing `resolvedBy` is kept and only `reply` is written), ONE save + ONE broadcast. Panel: the resolved row's meta says `You replied: <first 80 chars>` (escHtml), the viewer the whole text; `resolvedByText('reply')` = t('by your reply'). A later `vibespace-ask resolve` of the same id by the agent is an idempotent no-op.

**D1.5 The availability ladder — one verdict, two projections.** PURE `replyVerdict({item, session}) → {ok:true} | {ok:false, code, why}` (`src/inbox-reply.js`); the server feeds the real session record's projection `{live, mode, remoteState}`, the client the `active-sessions` payload's; codes and sentences agree:

| Case | Client | Server |
|---|---|---|
| key `accounts` / `jobs`, or `item.jobId` (the answer surface is the job panel / Manage Agents) | button **not rendered** | 409 `no_session` / `job_item` |
| session not in activeSessions (not running) | disabled, tooltip "Agent not running — open the session, then reply" | 409 `no_live_session` |
| `mode !== 'chat'` (a terminal session) | disabled, tooltip "Terminal session — reply in its window" | 409 `not_chat` |
| `remoteState` non-null (host unreachable) | disabled, tooltip "Host unreachable — reconnect, then reply" | 409 `host_unreachable` |
| normal (idle or mid-turn) | enabled | sent |

Mid-turn is not disabled: the frame is written and the session's own send mode takes over (queue by default; codex's queue strip shows it; claude's CLI queues it itself). The client verdict only sets the button's state; the server verdict is the real gate (a few seconds of staleness between two clients lands there).

**D1.6 A failure reaches the user.** `fetchJson` never throws ⇒ the panel checks `r?.ok`; every non-ok toasts `Could not reply: <why>` (the `replyVerdict` sentence, or the route's `error`); code table: `not_found` 404 · `empty`/`too_long`/`input_rejected` 400 · `no_session`/`job_item`/`no_live_session`/`not_chat`/`host_unreachable` 409 · `agent_forbidden` 403 · `send_failed` 500 (pty.write threw). The reply box keeps its text.

**D1.7 The running dot = an existing fact + one column.** Server `src/server/turn-facts.js`: PURE `turnOf(s)` = `s._turnState==='requires_action' ? 'waiting' : s._isStreaming ? 'running' : 'idle'`; `turnDigest(activeSessions)`; ONE 1 s unref'd timer in server.js: `broadcastActiveSessions()` only when the digest changed — **derived, not written at the 9 flip sites** (view-visibility.js's "derived, never written" rule). The payload gains `turn`; the sidebar's `LIVE_SESSION_FACTS.turn: {digest:null}` (carried-only — a fact that changes twice per turn would, if gating, reintroduce the 2.72.0/2.106.1 list-re-render churn; no card draws it). Client PURE `liveDotState({live, remoteState, mode, turn})` (`user-todos-layout.js`) → `running` filled green · `idle` hollow green · `waiting` hollow amber (the harness's own requires_action = "paused on you") · `unreachable` dashed grey · `off` filled grey; one tooltip sentence each. The panel subscribes to `active-sessions` and only patches `.ut-live-dot[data-key]`'s `data-state`/title — keyed chips, no row re-render.

**D1.8 The chat card.** In the CLI and the transcript this is a user message (`typed:true`); the renderer recognises the marker line **from the text** (`parseReply`) ⇒ card head `For you · reply to #<id>` + the quote folded in a `<details>` (collapsed) + the reply body. Text-derived ⇒ live stream and history agree (the 2.369.112 both-carriers rule); no new originKind.

**D1.9 Multi-client and in-place repaint.** Every change still rides the ONE `user-todos-updated` broadcast; the panel becomes **keyed rows**: `renderPanel` patches existing `.ut-item[data-id]` (dot / meta / resolved state / chips), appends new rows, removes vanished ones; **a reply box with focus or text is never replaced** (the a3 keyed-chips rule + inc-mtw02kbq-kj96's slot rule). `user-todos-layout.js`'s slot algorithm is unchanged; its consumer reconciles DOM instead of producing an HTML string.

**Future (listed, not built):** ① "stash for the next turn" when the agent is not running (ladder rung 3 + a `pendingReply` on the item; a stash goes through the ladder and the authorizer — owner decides first); ② terminal-session replies (keystrokes into a TUI whose mode is unknown — dangerous); ③ replying from the notification toast.

## §3 D2 The mini inbox in a chat window's title bar

- `window.js` `setInboxBadge(id, {count, urgency})` — `setOwnerBadge`'s twin: `win._inboxBadge`, key `count:urgency`, a `.win-inbox-badge` button after titleSpan (`UI_ICONS.inbox` + the number, coloured by `data-urgency`), removed at 0; drawn on the tab by `_renderTabBar` when grouped (`_inboxBadgeEl` beside tab-group.js's `_ownerBadgeEl`); `setTitle` does not wipe it (a sibling of titleSpan).
- Data: the panel module is the client's ONE item store (`todos`); it keeps `keyByWebuiId` (from the `active-sessions` payload's `sessionKey`, plus `webui:<id>`) and after every `apply()` and every `active-sessions` walks `app.sessions` (winId → view, `view.sessionId` = webuiId) calling `setInboxBadge` per window (chat/terminal session windows only; count = that key's open **action** items, notices excluded).
- Click ⇒ `openMiniInbox(anchorBtn, sessionKey)`: `createPopover(anchor, 'ut-mini-popover', …)` (carries `data-popover` ⇒ the global layered Esc closes it before the panel), content = **the same row renderer** `renderRows(entries, {mini:true})` filtered to that key (including its resolved-in-place rows, the same slot rule, append-only for the popover's lifetime); every action identical (reply / options / ✓ / ✕ / ↺ / ⤢); **jump is a no-op** (this is the window); a broadcast reconciles the popover in place.
- Phone: the same title-bar badge; the popover follows the `.usage-popup` full-width sheet rule; the panel sheet gets the same reply box (one renderer, no second copy).
- Keyboard shortcut: optional, not built (the Ctrl+\ prefix table is full; listed as future).

## §4 D3 Raising usage — each option scored

Score: value / cost / risk / now vs later.

| # | Option | Value | Cost | Risk | Decision |
|---|---|---|---|---|---|
| a | **Option chips** `--options "A|B|C"` (≤6, ≤40 chars each, deduped; one-click reply with the label; the quote carries an `options:` line) | high (decisions are most asks; one click) | medium (CLI + route + store validation + chips + manual + teaching line) | low | **now** (chunks 1+2) |
| b | **Inline one-line reply** (Enter sends, Shift+Enter newline, Esc folds, text survives broadcasts) | high | medium | low | **now** (chunk 2) |
| c | "Answered elsewhere" auto-resolve (the owner types in that chat within N min ⇒ resolve its open items) | medium | low | **high**: false resolves (the typed text is unrelated; one session, several asks, one answered) ⇒ trains the user to ignore the inbox — the very disease | **later**; instead: the agent is already taught `resolve`, the Stop hook nudges; the mini badge is itself the reminder |
| d | **Flood folding**: a group with > 5 open shows the newest 5 + "N more…" (expansion remembered while open); **per-agent "Mark all seen"** (`POST /api/user-todos/resolve-many {ids, status:'dismissed'}`, ONE broadcast) | high (the owner's complaint #1 is volume) | medium | low (dismiss is ↺-able) | **now** (chunk 4) |
| e | Expiry of stale items from dead sessions (the spend-notice `expiresAt` precedent) | medium | low | medium: a remote/offline host's session "unseen" ≠ dead; an ask does not stop needing an answer because the agent stopped | **later**; never inferred — if built, producer-declared (`vibespace-ask --expires 24h`) |
| f | **Decisions-first ordering**: within an urgency, items with `options` first (the store's `snapshot()` sort key, every client agrees) | medium | tiny | none | **now** (chunk 1) |
| g | Keyboard j/k/r/d | low-medium | low | low | later |
| h | **Board-state chip**: the `session-status` state (needs-input / blocked / review / working) beside the group name (the client already holds `_sessionStatuses` and its broadcast) | medium | low | none | **now** (chunk 4) |
| i | Per-agent mute | low | medium | medium (it mutes items that NEED you) | later; d answers the flood |

The trimmed set built now = a + b + d + f + h.
